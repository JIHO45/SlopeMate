# 03. 요구사항

작성: 2026-11-08 · 깊이: 충실히 · 상태: 승인 (2026-11-08)

이 문서는 **트래킹 앱 첫 출시(버전 2.0)** 의 범위를 정한다. 기존 앱스토어 등록(SlopeMate)을 업데이트로 이어 쓴다. **이번 시즌 개장(2026년 11월 말)에 P0 전체와 날씨(R33)·예상 설질(R39)을 2.0으로 출시한다.** 슬로프 이름 표시(R9)만 출시 후 리조트별로 켠다(8장). 01-idea의 아이디어와 02-market의 결론을 바탕으로 한다.

## 1. 문제

스키장에 자주 가는 사람은 오늘 몇 번, 어느 슬로프를 탔는지, 이번 시즌 얼마나 탔는지 남기고 싶다. 해외 트래킹 앱은 국내 스키장의 슬로프와 야간·심야 운영을 잘 다루지 않고, 국내 앱은 기록보다 커뮤니티나 랭킹 점수에 집중한다. 그래서 국내 스키어의 시즌 기록은 기억과 사진에 흩어져 있다.

## 2. 목표

| # | 목표 | 성공 판단 |
| --- | --- | --- |

**지원 기기 (제안값):** iOS 17 이상 iPhone.

## 4. 사용자 시나리오

**시나리오 A: 시즌권자의 평일 야간**
지수는 곤지암 시즌권자다. 처음 앱을 열어 홈 리조트로 곤지암과 가끔 가는 지산을 고르고, 시즌권 가격과 하루 리프트권 가격을 넣었다. 퇴근 후 19시에 도착해 기록을 시작하고 휴대폰을 주머니에 넣는다. 리프트에서 잠금 화면의 기록 카드를 눌러 앱을 열자, 맨 위에 "방금: 레드 슬로프 · 설질?" 칸이 있어 "아이스"를 누른다. 22시 반에 기록을 끝내자 "야간 · 14회 · 18.2km"와 하강 목록이 나온다. 시즌 화면에는 "9일째 · 1회 방문당 31,000원"이 보인다.

**시나리오 B: 기록 중 앱이 종료됨**
민호는 점심을 먹다가 휴대폰 배터리가 꺼졌다. 충전 후 앱을 열면 꺼지기 직전까지의 기록이 남아 있고, "기록이 중간에 끊겼어요. 이어서 기록할까요?"가 뜬다. 끊긴 시간은 "기록 없음"으로 보인다.

**시나리오 C: 크루 비교**
지수는 크루 "목요야간"을 만들고 초대 링크를 단톡방에 올린다. 크루원 4명이 들어오자 크루 화면에 이번 시즌 방문일, 횟수, 거리 순위가 나온다. 가입 화면에서 "가입 전 이번 시즌 기록도 크루에 공유됩니다"라는 안내를 본다.

**시나리오 D: 다른 리조트 방문**
지수가 주말에 하이원에 간다. 기록을 시작할 때 이번 기록의 리조트만 하이원으로 바꾼다. 홈 리조트 목록은 그대로다. 하이원의 슬로프 이름이 아직 켜지지 않았다면 슬로프 이름 없이 기록되고, 주간·야간 구분과 횟수·거리는 그대로 나온다. 시즌권 본전 계산에는 곤지암 방문만 들어간다.

## 5. 집계 규칙 (모든 화면과 크루 순위가 같은 규칙을 씀)

| 항목 | 규칙 (제안값) |
| --- | --- |
| **하강 1회** | 리프트 하차 후 다음 리프트 탑승(또는 기록 종료)까지 고도가 일정 이상(예: 30m) 내려간 이동. 슬로프를 이어서 내려오면 1회. 기준값은 현장 테스트로 조정 |
| **방문일** | 하강이 1회 이상 있는 **영업일** 1일. 같은 영업일에 기록을 여러 번 해도 1일 |
| **영업일** | 06:00~다음 날 06:00. 자정 이후 심야 하강은 전날 영업일에 속함 |
| **하루 두 리조트** | 방문일은 1일. 리조트별 합계에는 각 리조트에 1일씩 |
| **거리** | 하강 구간의 수평 이동 거리 합. 리프트 이동과 기록이 끊긴 구간은 넣지 않음 |
| **평균 속도** | 하강 구간에서 멈춰 있던 시간을 뺀 평균 |
| **시즌** | 11월 1일~다음 해 4월 30일 |
| **시즌권 본전** | 시즌권마다 그 시즌권의 대상 리조트 방문일만 셈. 한 시즌권에 대상 리조트를 여러 개 지정할 수 있음. 한 리조트가 두 시즌권에 모두 들어 있으면 목록에서 위에 있는 시즌권에만 셈(순서는 사용자가 바꿈). 전체 합계는 모든 시즌권 가격의 합 ÷ 시즌권으로 간 방문일(같은 날 두 리조트는 1일) |

## 6. 요구사항

### 리조트별 지원 범위

리조트 수를 미리 제한하지 않는다. 기능마다 필요한 데이터가 달라서, 기능별로 켜는 조건을 둔다. 리조트 데이터 이용 문의의 결과는 실시간 슬로프 현황(P1 이후)에만 영향을 준다.

| 기능 | 켜지는 리조트 | 필요한 데이터 | 리조트 허락 |
| --- | --- | --- | --- |
| 기록, D1 시즌권 본전, D5 크루 | 모든 국내 리조트 | 없음 | 필요 없음 |
| D2 주간·야간·심야 세션 | 시간표를 입력한 리조트 (출시 때 전체 목표) | 리조트가 공개한 운영 시간을 손으로 입력 | 필요 없음 |
| R9 슬로프 이름 표시 | 현장 테스트를 통과한 리조트부터 하나씩 | OpenStreetMap 슬로프·리프트 데이터 | 필요 없음 (출처 표시) |
| D3 설질, D4 리프트 대기 수집 | 기기 안에서 슬로프·리프트를 식별할 수 있는 리조트 | OpenStreetMap | 필요 없음 |
| 실시간 슬로프 현황 (열림/닫힘) | 서면으로 허락한 리조트만 | 리조트 홈페이지 | **필요함** |

우선순위: **P0** 첫 출시에 반드시 필요 · **P1** 출시 직후 · **P2** 사용자가 모인 뒤, 지금은 설계만 고려

### P0: 이번 시즌 첫 출시

**기록**

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| R1 | **홈 리조트 직접 선택** | 첫 실행 때 국내 리조트 목록에서 홈 리조트를 **여러 개** 고를 수 있다. 기록을 시작할 때 홈 리조트 중 하나를 고르고, 마지막으로 기록한 리조트가 기본값이다. 목록에 없는 리조트도 이번 기록에만 고를 수 있다. GPS로 리조트를 미리 고르거나 확인하지 않는다. |
| R2 | **기록 시작·종료** | 시작 버튼 한 번으로 기록이 시작된다. 화면이 꺼지거나 다른 앱을 써도 기록이 계속된다. 종료 버튼으로 끝낸다. |
| R3 | **라이딩·리프트 자동 구분** | 5장 규칙으로 하강을 나누고, 하강마다 시작 시각, 거리, 고도차, 최고·평균 속도를 남긴다. G3 기준을 만족한다. |
| R4 | **기록 보존** | **받은 위치 데이터**는 받는 즉시 기기에 저장해, 강제 종료·시스템 종료·방전 시 잃는 범위가 최대 1분 (제안값)이다. 휴대폰이나 앱이 꺼져 있어 **받지 못한 시간**은 이 약속에 포함되지 않으며, "기록 없음" 구간으로 표시하고 거리를 추정해 채우지 않는다. 다시 열면 이어서 기록할지 묻고, 이어서 기록해도 하강이 중복되지 않는다. 앱 업데이트 후에도 기록이 남는다. 저장 공간이 부족하면 기록 시작 전에 알리고, 기록 중 저장에 실패하면 기록을 멈추고 알린다. 서버 연결 없이도 기록된다. |
| R5 | **하루 기록 화면** | 합계(횟수, 거리, 고도차, 최고 속도)와 하강 목록을 보여준다. 세션이 있으면 세션별로 나눈다. |
| R6 | **시즌 기록 화면** | 이번 시즌의 방문일, 횟수, 거리를 리조트별로 보여준다. 슬로프 이름이 켜진 리조트는 슬로프별 횟수도 보여준다. |
| R7 | **D2 주간·야간·심야 세션** | 리조트별 날짜별 운영 시간표로 각 하강을 세션에 배정한다. 시간표 밖의 하강은 "미분류"로 둔다. 시간표가 없거나 오래된 리조트는 세션을 나누지 않는다. 시간표를 고치면 지난 기록도 다시 분류된다. 모든 리조트의 시간표를 리조트가 공개한 정보에서 손으로 입력해 준비한다(자동 수집하지 않음). 이 준비가 요구사항에 포함된다. |
| R8 | **D1 시즌권 본전 계산** | 시즌권을 **여러 장** 등록할 수 있다. 시즌권마다 이름, 가격, 하루 리프트권 가격, 대상 리조트(여러 개 가능)를 입력하면 "1회 방문당 금액"과 "리프트권으로 샀다면 쓴 금액"을 보여준다. 2장 이상이면 전체 합계도 보여준다(5장 규칙). 등록한 시즌권이 없으면 카드를 숨긴다. 대상 리조트 방문일이 0일인 시즌권은 계산하지 않는다. |
| R9 | **슬로프 이름 표시 (조건부)** | OSM 기반 슬로프 데이터로 하강에 슬로프 이름을 붙인다. 난이도는 데이터에 있을 때만 보여준다. 애매하면 "알 수 없는 슬로프"로 둔다. 현장 테스트에서 **이름 정답률과 이름을 붙인 비율**이 둘 다 기준을 넘을 때만 리조트별로 켠다 (기준은 06-verification). 표시를 꺼도 D3에 쓸 슬로프 식별은 기기 안에서 계속한다. OSM 출처를 앱 안에 표시한다. |

| --- | --- | --- |
| R10 | **D4 리프트 대기 표본 수집** | 탑승장 근처에서 머문 뒤 **실제로 그 리프트를 탔을 때만** 대기 시간으로 잰다. 탑승으로 이어지지 않은 체류(식사, 일행 기다리기)는 대기로 세지 않는다. 판단이 안 되면 표본을 버린다. 현장에서 직접 잰 대기와 비교해 오차를 06-verification 기준 안에 둔다. 사용자 화면에는 보여주지 않는다. |
| R11 | **D3 설질 평가 칸** | 하강을 감지하면 앱 안 기록 중 화면 맨 위에 "방금: ○○ 슬로프 · 설질 [아이스] [적당함] [슬러시]" 칸을 띄운다(제안값). 알림이나 잠금 화면 버튼은 쓰지 않는다. 사용자가 앱을 열었을 때만 보이고, 답하지 않아도 된다. 슬로프와 시간대는 방금 하강에서 자동으로 붙는다. 슬로프를 식별하지 못한 하강은 칸을 띄우지 않는다. 다음 하강을 감지하면 칸이 새 슬로프로 바뀐다. 하강 후 30분이 지나면 칸을 닫는다. 설정에서 끌 수 있다. |
| R12 | **익명 표본 전송** | R10·R11 표본에는 리조트, 리프트 또는 슬로프 ID, 한국 시간 기준 날짜와 15분 단위 시간대, 대기 시간 또는 설질만 담는다. 계정, 기기 식별자, 정확한 시각, 좌표는 넣지 않는다. 서버는 받은 즉시 시간대별 집계 숫자만 올리고 **개별 표본은 저장하지 않는다.** 서버 요청 로그는 남기지 않거나 하루만 보관한다. 처음 기록을 시작할 때 익명 표본 전송 동의를 받고, 설정에서 끌 수 있다. 끄면 아직 안 보낸 표본은 버리고, 다시 켜도 과거 표본은 보내지 않는다. |

**계정과 크루**

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| R13 | **계정** | 크루를 쓸 때만 Sign in with Apple로 가입한다. 가입 없이도 기록은 모두 쓸 수 있다. 앱 안에서 계정을 삭제하면 서버의 계정, 활동 합계, 크루 소속이 지워지고, Apple 로그인 연결도 해제되며, 완료를 알려 준다. 삭제 후 기기에 남아 있던 업로드 대기 데이터가 서버로 다시 올라가지 않는다. |
| R14 | **D5 크루** | 크루를 만들고 초대 링크로 사람을 모은다. 크루 인원은 최대 50명, 한 사람이 만들 수 있는 크루는 5개다. 정원이 차면 "크루가 가득 찼어요"를 보여준다. 크루 화면에 이번 시즌 크루원별 방문일, 횟수, 거리 순위와 마지막 갱신 시각을 보여준다. 가입 전 "이번 시즌 기록이 크루원에게 보인다"고 안내한다. 크루장은 초대 링크를 새로 만들어 이전 링크를 무효화할 수 있다. 크루를 나가면 그 크루에서 내 기록이 사라지고, 나간 사람은 크루 기록을 볼 수 없다. 크루장이 나가면 다음 가입자가 크루장이 된다. 가입·탈퇴·추방·크루장 변경은 서버에서 처리한다. |
| R15 | **크루 동기화** | 같은 기록을 여러 번 보내도 합계가 늘지 않는다. 서버에 못 보낸 합계는 기기에 남았다가 연결되면 보낸다. 동기화에 실패하면 크루 화면에 알린다. 다른 크루의 기록은 볼 수 없다. |
| R16 | **크루 이름 관리** | 크루 이름과 표시 이름에 부적절한 내용을 신고하고 크루원을 내보낼 수 있다. 앱 안에 문의 연락처를 둔다. |

**개인정보와 출시 요건**

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| R17 | **서버로 보내는 데이터 제한** | 계정과 함께 보내는 데이터는 **이번 시즌 합계(방문일, 횟수, 거리)와 리조트별 방문일 수**뿐이다. 날짜별 기록은 서버에 저장하지 않는다. GPS 좌표, 경로, 하강별 기록은 **우리 서버와 분석·오류 수집 도구로 보내지 않는다.** 익명 표본은 R12 규칙만 따른다. |
| R18 | **위치·동작 권한** | 권한을 요청하기 전에 왜 필요한지, GPS 기록이 우리 서버로 가지 않는다는 것을 설명한다. 권한 거부, 정확한 위치 끔, 위치 서비스 전체 끔, 기록 중 권한 변경을 각각 감지해 기록할 수 없는 이유와 설정 방법을 안내한다. 정확한 위치가 꺼져 있으면 기록을 시작하지 않는다. 고도 측정용 **동작 및 피트니스 권한**도 요청한다. 거부하거나 기압계가 없으면 GPS 고도로 대신 기록하고 하루 기록에 "고도 정확도 낮음"을 표시한다. |
| R19 | **고지와 동의** | 개인정보처리방침에 계정 데이터, 크루 공유 항목, 익명 표본의 수집 항목·목적·보유 기간을 적고 앱과 앱스토어에 건다. 앱스토어 개인정보 항목을 실제 전송과 일치시킨다. |
| R20 | **연령** | 계정 가입(크루)은 만 14세 이상만 할 수 있다. 가입 시 확인한다. 가입 없는 기록은 개인정보가 우리 서버로 오지 않으므로 연령 확인을 하지 않는다. |
| R21 | **최소 접근성** | VoiceOver와 큰 글씨 설정에서 기록 시작·종료, 계정 삭제를 할 수 있다. |
| R22 | **테스트 기록 내보내기 (TestFlight 빌드 전용)** | 테스터가 하루 기록 화면에서 GPS 원본을 포함한 기록 파일을 직접 내보내 공유할 수 있다. 내보내기 전에 "위치 기록이 포함된다"고 알리고 동의를 받는다. 앱스토어 빌드에는 들어가지 않는다. 받은 파일은 분석 후 삭제한다 (기간은 06-verification). 테스터의 위치 기록을 받는 일이 위치정보법상 문제가 없는지 B4 문의 때 함께 확인한다. |
| R23 | **Live Activity 기록 상태** | 기록 중에는 잠금 화면과 다이나믹 아일랜드에 경과 시간, 하강 횟수, 거리를 보여준다. 버튼은 넣지 않는다. 누르면 앱의 기록 중 화면이 열린다. 기록이 멈추면(권한 꺼짐 등) 표시한다. Live Activity는 최대 8시간만 갱신되므로, 8시간이 지나면 "기록 중 · 앱을 열면 다시 표시"로 끝낸다(이 카드가 계속 보인다고 약속하지 않음). **기록은 계속되고**, 사용자가 앱을 열면 새 Live Activity를 시작한다. 사용자가 Live Activity를 꺼도 기록은 계속된다. |

## 8. 일정 고려

- 국내 스키장은 11월 하순부터 순차 개장한다. 트래킹은 눈 위에서만 검증할 수 있다.
- **출시 순서: 개장(11월 말)에 P0 전체와 날씨(R33)·예상 설질(R39)을 2.0으로 낸다.** 슬로프 이름(R9)은 코드는 넣되 표시를 꺼 두고, 리조트별로 현장 검증을 통과하면 서버 설정 파일로 켠다. 11월 22일쯤 안정되지 않은 기능은 빼고 제출하고 개장 후 업데이트로 낸다. 테스터는 TestFlight로 한발 앞선 빌드를 쓴다. 11월 25일쯤 심사 제출을 목표로 하고, TestFlight 외부 테스트 심사와 앱스토어 심사 시간을 일정에 더한다. 심사자는 스키장에 갈 수 없으므로 녹화 영상이나 시연용 재생 기능 같은 심사 자료가 필요할 수 있다.
- **테스터가 검증하려면 기록을 받아 볼 방법이 필요하다.** GPS 기록은 우리 서버로 오지 않으므로, TestFlight 빌드에만 테스터가 직접 자기 기록 파일을 내보내 보내 주는 기능을 둔다(R22). 테스터는 직접 센 하강 횟수와 리프트 대기 시간도 함께 적어 보낸다.
- P0가 23개이고, 계정·크루(R13~R16)에 서버가 필요하다. 주 40시간 1인 개발 기준의 일정은 05-design에서 기능별로 추정한다.
- **잘라야 할 때의 순서 (제안):** R9 슬로프 이름 표시 → R10·R11·R12 익명 표본 수집 → R8 시즌권 본전. **R14 크루는 자르지 않는다.** 크루는 2.0에 넣고, 늦어지면 개장 후 업데이트로 이번 시즌 안에 낸다.
