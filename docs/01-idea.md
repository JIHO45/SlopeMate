# 01. 아이디어

작성: 2026-11-07 · 상태: 검토 대기

## 한 줄 요약

국내 스키장에서 **오늘 어느 슬로프를 몇 번, 얼마나 탔는지** 자동으로 기록하고, 시즌 내내 쌓인 기록을 보여주는 iOS 앱. 날씨와 운영 시간은 보조 기능으로 제공한다.

**국내 전용 앱이다.** 국내 스키장만 지원하고, 시즌권·야간·심야 운영·크루 문화처럼 국내 스키 환경에 특화한 기능으로 차별화한다. 해외 진출은 앱이 자리 잡은 뒤의 장기 목표로만 둔다.

**iPhone부터 만든다.** iPhone에서 반응이 좋으면 안드로이드를 추가한다. 순서는 iPhone → 안드로이드 → 해외(일본, 캐나다 등)다. 안드로이드는 확정이 아니라 가능성으로 두되, 설계가 iPhone에만 묶이지 않게 한다.

## 1. 문제

| 하고 싶은 것 | 지금 하는 방법 | 불편한 점 |
| --- | --- | --- |
| 오늘 몇 번, 얼마나 탔는지 알기 | Slopes 같은 해외 트래킹 앱, 워치 운동 기록 | 국내 슬로프 이름과 리프트를 제대로 인식하는지 불확실함 (확인 필요) |
| 시즌 동안 얼마나 탔는지 보기 | 기억, 메모, 사진 | 리조트별·시즌별로 쌓이지 않음 |
| 어려운 코스에 도전하고 있는지 보기 | 감으로 판단 | 기준이 없음 |
| 오늘 열린 슬로프 알기 | 리조트 홈페이지, 커뮤니티 | 리조트마다 위치와 형식이 다름. 리조트 데이터를 가져오려면 허락이 필요함 |
| 함께 탄 사람과 기록 나누기 | 스크린샷 공유 | 비교하거나 쌓이지 않음 |

## 2. 대상 사용자

| 유형 | 이 앱에서 얻는 것 | 우선순위 |
| --- | --- | --- |
| **시즌권자·자주 가는 사람** | 시즌 누적 기록, 리조트·슬로프별 통계, 비교 | **1순위.** 자주 타므로 기록이 빨리 쌓이고, 기록을 남길 이유가 가장 크다 |

## 3. 해결할 일 (JTBD)

1. 스키장에 도착했을 때, 시작 버튼 한 번으로 오늘 탄 기록을 남기고 싶다. 그래야 타는 데만 집중할 수 있다.
2. 하루가 끝났을 때, 어느 슬로프를 몇 번, 얼마나 빨리 탔는지 보고 싶다. 그래야 오늘 하루를 돌아보고 자랑할 수 있다.
3. 시즌 중에, 이번 시즌 몇 번 갔고 얼마나 탔는지 보고 싶다. 그래야 시즌권 값을 했는지, 더 어려운 코스에 도전하고 있는지 알 수 있다.
4. 같이 타는 사람들 사이에서, 내가 얼마나 탔는지 비교하고 싶다. 그래야 더 타고 싶어진다.
5. 출발 전에, 오늘 바람이 세서 리프트가 멈출지 알고 싶다. 그래야 헛걸음하지 않는다. (보조 기능)

**감정적인 일:** "이번 시즌 이만큼 탔다"는 성취감. 크루나 친구에게 보여줄 수 있는 기록.

**약속하지 않는 것:** 거리, 횟수, 속도는 활동량이지 실력의 직접 근거가 아니다. "실력 향상"이 아니라 "활동량과 도전한 코스의 변화"로 표현한다.

## 4. 기능 구성 (초안, 03-requirements에서 확정)

**핵심 (기본 기록은 국내 스키장 기준으로 Slopes 수준을 목표로 한다)**
- 자동 트래킹: 라이딩과 리프트 탑승을 구분하고, 거리·속도·고도·횟수를 기록
- **기록 보존:** 화면 잠금, 앱 종료, 통신 두절, 배터리 방전이 있어도 그때까지의 기록을 잃지 않음. "시작 버튼 한 번"은 이 약속까지 포함한다.
- 국내 슬로프 인식: 탄 구간을 슬로프 이름과 난이도로 표시. 애매하면 이름을 억지로 붙이지 않음
- 하루 기록과 시즌 기록: 리조트별, 슬로프별 누적

**비교와 랭킹 (단계적으로)**
1. 개인 시즌 목표 (예: 이번 시즌 20일, 100회)
2. 친구·크루 같은 작은 그룹 안 비교
3. 크루끼리 경쟁과 보상, 리조트별 공개 랭킹은 사용자가 충분히 모인 뒤에 검토

- 랭킹은 **활동량 순위**다. 실력 순위로 보이지 않게 한다.
- 최고 속도 경쟁은 만들지 않는다. 안전 문제가 있다. 보상도 활동량(방문일, 횟수, 거리) 기준으로만 준다.
- 보상의 형태(배지 같은 앱 안 보상, 리조트·제휴처 혜택 등)는 TBD.
- 시작 전에 정할 것: 방문일을 어떻게 세는지(주차장만 들러도 방문인가, 하루에 기록을 여러 번 켜면), 심야는 어느 날짜인지, 연결 슬로프를 이어 내려오면 1회인지, 리프트 이동 거리는 빼는지, 수동 수정한 기록을 인정하는지, 오류 기록에 이의를 어떻게 받는지

**핵심 기록에서 나오는 것 (나중에)**
- "최근 사용자 주행이 감지된 구간": 관측 시각과 표본 수를 함께 표시한다. **열림/닫힘이나 혼잡도로 표시하지 않는다.** 오전에 탄 기록이 오후 개방을 보장하지 않고, 기록이 없다고 닫힌 것도 아니다.

**차별점: 국내 스키 환경에 맞춘 기능**

| # | 기능 | 내용 | 성격 |
| --- | --- | --- | --- |
| D1 | 시즌권 본전 계산 | 시즌권 가격을 입력하면 "오늘까지 1회당 얼마"를 보여주고 리프트권 정가와 비교 | 국내 기본기. Slopes에 비슷한 기능이 있을 수 있어(02-market) 사람을 옮겨 오게 할 이유로는 기대하지 않음 |
| D2 | 주간·야간·심야 세션 기록 | 리조트 운영 시간 기준으로 세션을 나눠 기록. 자정을 넘기는 심야는 전날 세션으로 묶음 | 첫인상. 리조트별 운영 시간 데이터 필요 |
| D3 | 슬로프별 시간대 설질 | 하강을 감지하면 앱 안 기록 화면 맨 위에 "방금 탄 슬로프 설질?" 칸이 생기고, 리프트에서 앱을 열었을 때 한 번 눌러 답함. 알림은 쓰지 않음. 앱이 아는 슬로프와 시각이 자동으로 붙음. 모이면 "이 슬로프 오후 2시 이후 아이스" 같은 정보가 됨. 설질 점수의 근거도 여기서 나옴 | 해자. 사용자 데이터라 복사할 수 없음. 사용자가 모여야 보여줄 수 있음 |
| D4 | 리프트 대기 시간 | 리프트 탑승장 앞 대기 구간에 머문 시간을 자동으로 재서 리조트·리프트·시간대별 대기 시간을 보여줌 | 해자. D3과 같은 조건 |
| D5 | 크루 기록 | 크루별 시즌 누적, 크루 안 순위, 같이 탄 날 기록. 사용자가 모이면 크루끼리 경쟁과 보상으로 확장 | 국내 기본기. 스노우라이브도 크루를 운영 중. 크루가 자리 잡으면 옮기기 어려움. 서버 필요 |
| D6 | 강습 기록 공유 | 강사가 수강생 기록을 보고 강습에 활용 | **TBD.** 출시 후 차근히 검토. 강습 업체와 제휴해 웹으로 연동하는 방식도 후보 |

- D3과 D4는 사용자가 적을 때 보여줄 것이 없다. 데이터는 처음부터 모으고, 화면 표시는 기준 인원을 넘는 리조트부터 시작한다.
- 랭킹의 "비교" 단계(친구·크루)와 D5는 같은 서버 기반을 쓴다.

**리조트 선택과 위치 데이터 구조**

12곳을 모두 보여주지 않는다. 사용자가 **홈 리조트**를 직접 고른다. 여러 개를 고를 수 있고, 기록을 시작할 때 그중 하나를 고른다. 시즌권자는 처음 한 번만 고르면 된다.

| 데이터 | 어디에 두나 | 이유 |
| --- | --- | --- |
| GPS 원본, 슬로프 인식 결과 | 기기 안에만 | 위치정보법상 개인위치정보. 서버로 보내지 않으면 위치기반서비스 신고 대상에서 빠진다는 해석이 있음 |
| 사용자가 직접 고른 리조트 | 서버 (계정과 함께) | 측위한 정보가 아니라 사용자가 입력한 정보라 위치정보에 해당하지 않는다는 해석. 개인정보보호법은 적용됨 |
| 횟수, 거리, 날짜 | 서버 (계정과 함께) | 장소가 없어 위치정보가 아님. 크루 기록과 비교에 사용 |
| D3 설질, D4 리프트 대기 (리조트·슬로프·시각 포함) | 서버 (계정과 분리, 익명) | GPS에서 나온 정보라 개인을 알아볼 수 없게 해야 함 |

- **리조트 값은 GPS로 정하지 않는다.** GPS로 리조트를 미리 골라 주거나, GPS로 확인해서 맞을 때만 보내면 서버에 간 값이 측위 결과가 된다.
- 고른 리조트와 GPS가 맞지 않으면 기기 안에서 "슬로프를 인식하지 못했어요"라고만 보여주고, 그 판단 결과는 서버에 보내지 않는다.
- 사용자가 리조트를 잘못 고르거나 일부러 바꿀 수 있다. 리조트별 비교에는 그만큼 오차가 생긴다. 아는 사람끼리 비교하는 크루에서는 감당할 수 있다.
- 위 해석은 위치정보지원센터에 이 구조를 설명하고 확인받는다 (8장 B4).

**보조**
- 리조트별 날씨, 운영 시간, 공식 현황·웹캠 링크
- 강풍 안내 (무료): 바람 강조와 공식 현황 연결. 리프트 운휴를 예측하지 않음

## 5. 현재 대안과 경쟁

| 대안 | 잘하는 것 | 약한 부분 (가설) |

**슬로프 인식은 차별점이 아니다.** Slopes는 OpenStreetMap 데이터로 1,500곳 이상의 리조트 지도를 만들었고(2024-11 발표), 용평 페이지도 있다. 같은 OSM을 쓰면 앞설 수 없다. 남는 차이는 무료와 한글 표시 정도인데, Slopes의 인터랙티브 지도는 연 $29.99 유료 플랜 전용이다. 이 차이는 쉽게 따라 잡힌다.

**차별점은 D2·D3·D4다.** 경쟁 앱 설명 어디에도 야간·심야 세션, 슬로프·시간대 단위 설질, 리조트·시간대별 리프트 대기 집계가 없다(02-market). D3·D4는 사용자 데이터가 쌓일수록 좋아져 따라 하기 어렵다. D1(시즌권)과 D5(크루)는 경쟁 앱과 겹쳐서 국내에 맞춘 기본기로 둔다.

## 6. 확인한 사실

**슬로프 지도 데이터 (OpenStreetMap, 2026-11-07 Overpass API 조회, 리조트 좌표 반경 3.5km)**

| 리조트 | 슬로프 요소 (이름 있음 / 난이도 있음) | 리프트 요소 |
| --- | --- | --- |
| 하이원 | 20 (18 / 18) | 9 |
| 모나용평 | 41 (31 / 38) | 21 |
| 알펜시아 | 32 (25 / 31) | 19 |
| 휘닉스 | 23 (22 / 23) | 8 |
| 비발디 | 14 (12 / 11) | 9 |
| 오투 | 13 (0 / 0) | 3 |
| 엘리시안 | 10 (10 / 10) | 6 |
| 곤지암 | 9 (9 / 0) | 5 |
| 지산 | 9 (0 / 9) | 5 |
| 에덴밸리 | 7 (7 / 7) | 3 |
| 웰리힐리, 무주 | 서버 과부하로 조회 실패 | |

- 조회 조건: `way["piste:type"="downhill"]`와 `way["aerialway"]`
- 조회한 10곳 모두 슬로프 선이 있고, 대부분 이름과 난이도까지 있다. 오투는 선만 있고 이름과 난이도가 없다. **지도를 처음부터 그리지 않고 OSM을 출발점으로 쓸 수 있다.**
- 한계
    - 요소 수는 실제 슬로프 수와 다르다. 하나의 슬로프가 여러 요소로 나뉘거나, 한 요소가 여러 슬로프에 걸칠 수 있다.
    - 용평과 알펜시아는 2km 거리라 숫자가 겹친다.
    - 선이 실제 슬로프와 맞는지, 이름이 한글인지, 분기와 합류가 어떻게 되어 있는지는 확인하지 않았다.
    - OSM 데이터는 ODbL 라이선스다. 출처를 표시해야 하고, 고친 데이터를 배포하면 공유 의무가 생길 수 있다. 05-design에서 확인한다.

| # | 가정 | 근거 | 위험도 | 가장 싼 검증 방법 |

**출시 전 해결 조건: 해도 되는가, 해낼 수 있는가**

| # | 가정 | 근거 | 위험도 | 가장 싼 검증 방법 |

| B4 | 4장의 데이터 구조(GPS는 기기 안, 리조트는 사용자가 직접 선택)라면 위치기반서비스 신고 없이 운영할 수 있다 | 위치정보법 제2조는 위치정보를 "측위된" 장소 정보로 정의함. 제9조는 개인위치정보를 다루지 않는 위치기반서비스를 신고 대상에서 제외함. 위치정보지원센터 안내는 기기 안에서만 쓰는 경우를 제외 사례로 듦. 신고가 필요해도 소상공인은 사업 개시 후 1개월간 면제되고, 이후 간소 신고가 가능함(제9조의2) | 높음 | 위치정보지원센터에 4장의 구조를 그대로 설명하고 신고 대상인지 문의. 리조트·날짜가 계정과 묶이면 방문 이력이므로 개인정보보호법 의무(동의, 처리방침, 삭제)는 지킴. 지도·분석·오류 수집 SDK로 위치가 새 나가지 않는지도 확인 |

**가장 위험한 가정은 B1이다.** 이미 잘 만든 트래킹 앱이 있는데 사람들이 옮겨 오거나 새로 기록을 시작할 이유가 있는지 모른다. 코드를 짜기 전에 시안으로 확인하는 것이 가장 싸다. B2·B3가 틀리면 제품이 성립하지 않고, B4·B8은 출시 전에 반드시 풀어야 한다.

**반대 입장에서 본 가장 강한 반론:** 트래킹은 정확도와 배터리가 전부인 분야다. 이미 수년간 다듬은 Slopes와 혼자서 이번 시즌 안에 경쟁하기 어렵다. 이 반론에 대한 답이 "국내 슬로프 인식과 국내 사용자 비교"인데, 둘 다 아직 검증되지 않았다.

### 이번 시즌 범위 (초안)

- 이번 시즌 개장(11월 말)에 2.0 출시: 기록, 시즌권, 세션, 크루, 설질 칸, 리프트 대기 수집, 날씨, 예상 설질. 테스터는 TestFlight로 현장 기록을 보냄
- 모든 국내 리조트에서 기록. 슬로프 이름은 현장 테스트를 통과한 리조트부터
- 수동 시작·종료, 기록 보존, 하루·시즌 합계
- D1 시즌권 본전 계산, D2 주간·야간·심야 세션 기록
- D3 설질 피드백과 D4 리프트 대기 시간은 데이터만 모으고 화면에는 보여주지 않음
- 슬로프 이름 인식은 정확도 기준을 넘을 때만 켬
- D5 크루 기록과 친구 비교 (2.0에 포함. 서버에는 4장 구조대로 합계와 직접 고른 리조트만 보냄)
- 공개 랭킹, 주행 감지 구간, 설질 점수는 이번 시즌에 하지 않음
- 함께 정할 것: 주당 개발 시간, 현장 방문 횟수와 비용, 서버·지도 비용 상한, 기록 오류 문의에 쓸 시간
